# ADR-0001: Autoload Architecture & Initialization Order

## Status

Accepted — 2026-08-09 (M0 foundation; approved by Creative Director)

## Summary

Ten GDD-mandated Autoload singletons own all game state, logic, and persistence in a strict
initialization order that resolves the DCS-before-GSM conflict. `GameConfig` boots first; DCS
boots before GSM so GSM's deferred signal subscription never misses `session_begun`.

## Context

### Problem Statement

Ten of the 14 MVP systems are explicitly mandated as Autoload singletons by their GDDs. With
ten singletons, boot order is a correctness constraint, not a convention: each Autoload's
`_ready()` reads other Autoloads, and GSM must subscribe to DCS signals. The two GDDs that pin
an order disagree with each other.

### Current State

- `GameConfig` GDD Rule 2 / EC-5 requires GameConfig first ("Autoload order must list GameConfig first").
- `GameStateManager` GDD Rule 10 requires GSM to be listed *after* DCS (signal-subscription safety).
- `Save & Load` GDD's Architectural Note lists `NPCRegistry → GameStateManager → DialogueConversionSystem → SaveLoadSystem` (GSM *before* DCS) — contradicts GSM Rule 10.

### Constraints

- Godot registers Autoloads in `project.godot` order; `_ready()` runs in registration order.
- All ten systems are single-instance singletons; no dependency-injection container exists.
- `src/CLAUDE.md` + coding standards prefer dependency injection over singletons for testability — resolved via the instance-testable method pattern below.
- Mobile target: boot must be deterministic and free of null-refs at startup.

### Requirements

- `GameConfig` is available to every other system at its `_ready()`.
- GSM never misses `session_begun` / `session_complete` from DCS.
- `SaveLoadSystem` boots after every Autoload its `load_game()` touches (`NPCRegistry`, GSM).
- New Autoloads can be added without silently breaking the chain.

## Decision

Register the ten Autoloads in `project.godot` in exactly this order:

| Order | Name | Script |
|-------|------|--------|
| 1 | `GameConfig` | `res://src/autoload/game_config.gd` |
| 2 | `TraitDatabase` | `res://src/autoload/trait_database.gd` |
| 3 | `DialogueDatabase` | `res://src/autoload/dialogue_database.gd` |
| 4 | `MobileTouchFramework` | `res://src/autoload/mobile_touch_framework.gd` |
| 5 | `NPCRegistry` | `res://src/autoload/npc_registry.gd` |
| 6 | `ConversionLogicEngine` | `res://src/autoload/conversion_logic_engine.gd` |
| 7 | `DialogueConversionSystem` | `res://src/autoload/dialogue_conversion_system.gd` |
| 8 | `GameStateManager` | `res://src/autoload/game_state_manager.gd` |
| 9 | `RivalFaithSystem` | `res://src/autoload/rival_faith_system.gd` |
| 10 | `SaveLoadSystem` | `res://src/autoload/save_load_system.gd` |

DCS boots before GSM (GSM Rule 10 is the explicit rule; the Save&Load note is corrected — see
Consequences). GSM connects its DCS signal subscriptions via `call_deferred("_connect_signals")`
so all Autoloads finish `_ready()` before any signal can fire.

Each Autoload script keeps its logic in **instance-testable methods** so GUT can instantiate
the script directly and drive it with synthetic inputs (CLE's pure `resolve()` is the exemplar);
the Autoload node is the runtime access pattern, not the only test surface.

### Architecture

```
project.godot  autoload = [
  GameConfig(1) → TraitDatabase(2) → DialogueDatabase(3) → MobileTouchFramework(4)
    → NPCRegistry(5) → ConversionLogicEngine(6) → DialogueConversionSystem(7)
    → GameStateManager(8) → RivalFaithSystem(9) → SaveLoadSystem(10)
]
                     ┌─ all downstream systems read GameConfig in _ready()
                     └─ GSM subscribes DCS signals via call_deferred after (7) exists
```

### Key Interfaces

```gdscript
# project.godot (autoload section — order is authoritative)
autoload/GameConfig="*res://src/autoload/game_config.gd"
autoload/TraitDatabase="*res://src/autoload/trait_database.gd"
autoload/DialogueDatabase="*res://src/autoload/dialogue_database.gd"
autoload/MobileTouchFramework="*res://src/autoload/mobile_touch_framework.gd"
autoload/NPCRegistry="*res://src/autoload/npc_registry.gd"
autoload/ConversionLogicEngine="*res://src/autoload/conversion_logic_engine.gd"
autoload/DialogueConversionSystem="*res://src/autoload/dialogue_conversion_system.gd"
autoload/GameStateManager="*res://src/autoload/game_state_manager.gd"
autoload/RivalFaithSystem="*res://src/autoload/rival_faith_system.gd"
autoload/SaveLoadSystem="*res://src/autoload/save_load_system.gd"
```

### Implementation Guidelines

- Do not reorder the list; insert new Autoloads only at positions that preserve the dependency chain.
- GSM connects signals with `call_deferred` and asserts both `NPCRegistry` and `DCS` exist before connecting.
- FaithSpread is **not** registered at M0 (not an MVP system); GSM Step 4 calls a no-op stub — see ADR-0008.
- M0 boot test: headless launch with a `_ready()` assertion in each Autoload that its dependencies resolve.

## Alternatives Considered

### Alternative 1: GSM before DCS (Save&Load note's original order)

- **Description**: Keep `NPCRegistry → GSM → DCS → SaveLoad` as written in the Save&Load GDD.
- **Pros**: No GDD edit required.
- **Cons**: Violates GSM Rule 10's explicit ordering rule; GSM risks a missed `session_begun` at boot if DCS is absent during GSM's `_ready()`.
- **Estimated Effort**: Same as chosen.
- **Rejection Reason**: GSM Rule 10 is the explicit, authoritative rule; signal-subscription safety wins over avoiding a one-line doc edit.

### Alternative 2: Lazy / deferred singleton access everywhere

- **Description**: No strict order; all Autoloads resolve dependencies lazily at first use.
- **Pros**: Flexible boot; order-independent code.
- **Cons**: Hidden null-refs, non-deterministic init, and it contradicts the GDDs' explicit "Autoload order must list GameConfig first" requirement.
- **Estimated Effort**: Higher — every access site needs guards.
- **Rejection Reason**: The GDDs mandate an order; determinism and startup safety are more valuable than flexibility at this scale.

## Consequences

### Positive

- Deterministic boot: every Autoload's `_ready()` can rely on its dependencies.
- GSM never misses DCS session signals (deferred connect after both exist).
- One authoritative order in `project.godot`; GDDs and entities.yaml point at it.
- The DCS-before-GSM conflict (architecture risk R4) is resolved with a one-line Save&Load GDD correction.

### Negative

- Boot order is rigid; adding an Autoload requires re-validating the chain (reviewed in `/architecture-review`).
- Singleton access is the runtime pattern — reviewers who prefer DI must accept the instance-testable-method compromise.
- A misordered Autoload fails at boot with a null-ref rather than a friendly error (mitigated by boot assertions).

### Neutral

- `project.godot` becomes the single source of truth for singleton registration.
- FaithSpread is deliberately absent at M0 (stubbed at GSM Step 4).
