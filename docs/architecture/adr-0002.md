# ADR-0002: Data Resource Model (Resource Classes, GameEnums, VillageDefinition)

## Status

Accepted — 2026-08-09 (M0 foundation; approved by Creative Director)

## Summary

All structured game data — NPC records, traits, archetypes, config domains, and village
definitions — is modeled as typed Godot `Resource` subclasses authored as `.tres` files, with
all shared enums consolidated into one `GameEnums` class so `.tres` authoring and typed signals
have a single resolvable home.

## Context

### Problem Statement

The 14 MVP GDDs define ~10 named data structures (`NpcRecord`, `NPCConnection`, `NPCAccessGate`,
`NPCArchetypeDefinition`, `TraitData`, `NPCFlavourData`, nine config domains) but never pin their
GDScript form. Three cross-cutting facts are unresolved: (a) enums are split across GDD owners
(`ConversionOutcome`/`DialogueApproach` in DCD, `BeliefState` in NPC CS) yet `.tres` files and
typed signals need one enum home; (b) the GDDs reference village data (`initialize_village(npc_definitions)`,
VMV map art) but no village data structure exists; (c) `social_influence_weight` was drifting onto
the NPC record until NPC CS Rule 1 moved it to the archetype definition.

### Current State

- No `src/` files exist; `design/registry/entities.yaml` already registers config-domain `.tres` paths and `ConversionOutcome` (renamed `PERSUADED`).
- `design/gdd/npc-character-system.md` Rule 8 defines `initialize_village(npc_definitions)` but no village data carrier is defined anywhere.
- NPC CS Rule 9 flags the `PERSUADED` rename (collision with `BeliefState.CONVERTED`); no shared enum class exists yet.

### Constraints

- GDDs pin runtime data paths under `res://assets/data/...` — data must live at `res://assets/`, not `src/data/`.
- `entities.yaml` rule: never read `.tres` directly outside the owning Autoload (`GameConfig` for config domains).
- `NPCFlavourData` must be returned as `.duplicate()` (DCD EC-6) — Resource semantics required.
- Godot 4.6 `Resource` + `class_name` are stable, pre-cutoff APIs.

### Requirements

- One GDScript form per GDD data structure, instantiable and serializable.
- Enums addressable by name in `.tres` authoring and typed signal payloads.
- Village scene data has a defined carrier (proposed: `VillageDefinition`).
- Config values stay data-driven (never hardcoded) and load through `GameConfig`.

## Decision

1. **Resource subclasses** under `src/resources/`, one per GDD structure: `NpcRecord`,
   `NPCConnection`, `NPCAccessGate`, `NPCArchetypeDefinition`, `NPCArchetypeTraitBonus`,
   `TraitData`, `NPCFlavourData`, `VillageDefinition` (proposed, new), plus nine config-domain
   resources under `src/resources/config/` (`ConversionConfig`, `TraitConfig`,
   `FaithSpreadConfig`, `RivalFaithConfig`, `ProgressionConfig`, `UITimingConfig`,
   `PortraitConfig`, `VillageMapConfig`, `HUDConfig`).
2. **`GameEnums`** — a plain script class (`class_name GameEnums`) at `src/core/game_enums.gd`
   hosting every shared enum: `BeliefState`, `DialogueApproach`, `ConversionOutcome`
   (**PERSUADED** — renamed), `TraitRarity`, `RelationshipType`, `NPCArchetype`,
   `OutcomeCaller`, `AlignmentSignal`, `GSMState`, `SwipeDirection`. GDDs keep authoring their
   enum *values*; the compiled single source is `GameEnums`.
3. **`VillageDefinition`** (proposed) — `village_id`, `npc_definitions: Array[Dictionary]`,
   `map_art_path`, `rng_seed`; hand-authored `.tres` per village at
   `res://assets/data/villages/village_01.tres`; feeds `NPCRegistry.initialize_village()`.
   Schema confirmation pending Creative Director (architecture Open Question #4).
4. **Authored data** lives under `res://assets/data/` as `.tres` (Godot 4.6 format 3), read only
   through owning Autoloads (`GameConfig` for config domains; `TraitDatabase` for traits;
   `DialogueDatabase` for dialogue; `NPCRegistry` for archetypes/village data).

### Architecture

```
src/resources/                        res://assets/data/
├── npc_record.gd        ────────►    (records constructed at runtime by NPCRegistry)
├── npc_connection.gd
├── npc_access_gate.gd
├── npc_archetype_definition.gd  ──►  npcs/archetypes.tres            (7 archetypes)
├── npc_archetype_trait_bonus.gd
├── trait_data.gd              ──►     traits/trait_database.tres     (16 traits)
├── npc_flavour_data.gd        ──►     dialogue/dialogue_database.tres (100 strings)
├── village_definition.gd      ──►     villages/village_01.tres       (proposed)
└── config/  (9 domain classes) ──►    config/*_config.tres           (9 files)
src/core/game_enums.gd  (class_name GameEnums — all shared enums)
```

### Key Interfaces

```gdscript
class_name NpcRecord extends Resource
var npc_id: String
var archetype: GameEnums.NPCArchetype
var assigned_traits: Array[String]          # hidden until revealed
var revealed_traits: Array[String]
var belief_state: GameEnums.BeliefState
var cooldown_turns_remaining: int
var recently_converted_turns_remaining: int
var approach_count: int
var approach_history: Dictionary
var social_connections: Array[NPCConnection]
var map_position: Vector2i
var access_gate: NPCAccessGate               # nullable
# NOTE: social_influence_weight lives on NPCArchetypeDefinition, NOT here (NPC CS Rule 1)

class_name VillageDefinition extends Resource
var village_id: String
var npc_definitions: Array[Dictionary]       # consumed by NPCRegistry.initialize_village()
var map_art_path: String
var rng_seed: int
```

### Implementation Guidelines

- Give every Resource `class_name`; author `.tres` with `script_class` headers (format 3).
- `NPCFlavourData` getters must return `duplicate()` copies (DCD EC-6).
- `GameEnums` holds values only — no behaviour; all systems reference it by `class_name`.
- Config Resources are loaded once by `GameConfig` and pulled at call time (never cached) — ADR-0005.
- Add entities.yaml constants for every new cross-system structure (Appendix D of the plan).

## Alternatives Considered

### Alternative 1: Plain Dictionaries everywhere

- **Description**: Carry all data as untyped `Dictionary`/`Array` with string keys.
- **Pros**: No class scaffolding; quick to write.
- **Cons**: No type safety, no editor inspection, no `.tres` authoring, runtime key-typo bugs, and `duplicate()` semantics for flavour data get messy.
- **Estimated Effort**: Lower initially, higher over the 14-system lifespan.
- **Rejection Reason**: 27 systems total — untyped data at this scale is a maintenance liability; the GDDs' `.tres` path contracts assume Resources.

### Alternative 2: A single monolithic `GameData` class

- **Description**: One class holding every structure as inner classes / dictionaries.
- **Pros**: One file, one import.
- **Cons**: Godot inner-class `class_name` resolution in `.tres` is fragile; violates separation of concerns; hurts testability.
- **Estimated Effort**: Similar.
- **Rejection Reason**: Resource-per-structure is the idiomatic Godot 4 pattern and matches the repo's `entities.yaml`/config-domain structure.

## Consequences

### Positive

- Typed, inspectable, serializable data — SaveLoad's `serialize()`/`deserialize()` gets clean round-trips.
- `GameEnums` resolves the cross-GDD enum coupling and the `PERSUADED` rename (architecture decision D9).
- `VillageDefinition` gives VMV/NPC CS a defined village data carrier (decision D10).
- `.tres` authoring (config, traits, dialogue, archetypes, villages) is editor-friendly and diff-friendly.

### Negative

- New Resource classes add scaffolding before logic can be written (absorbed into M1/M2).
- `VillageDefinition` schema is proposed, not yet confirmed — first village content is blocked on Creative Director sign-off (Open Question #4).

### Neutral

- `entities.yaml` becomes the cross-doc registry for these structures (path, owner, referenced_by).
- Resource scripts are data carriers with no lifecycle — ownership stays with the constructing Autoload.
