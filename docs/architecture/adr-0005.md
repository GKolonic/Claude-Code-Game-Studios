# ADR-0005: Config System (Nine Domains, Pull Pattern, Validation, Editor-Only Hot-Reload)

## Status

Accepted — 2026-08-11 (Sprint 1 task 1-8; Creative Director delegation per OQ-6: ADR written at Sprint 1 start and Accepted before 1-10 begins)

## Summary

All tunable game values live in nine typed `.tres` config-domain resources read exclusively by the `GameConfig` Autoload (slot 1 of the ADR-0001 order). Systems pull values at call time via `GameConfig.[domain].[field]`; `GameConfig` validates/clamps every field on load, hard-halts on missing files or required fields, and hot-reloads `.tres` changes in the editor only (no file watcher in export builds).

## Context

### Problem Statement

Fourteen MVP GDDs reference ~50 tuning values (success chances, timings, thresholds, weights) that must never be hardcoded in GDScript (GameConfig Rule 1 / AC-6). Without a single config authority, values drift across GDDs (R2 is a live example), systems cache stale numbers, and designers cannot tune without a rebuild. The decision must pin: (a) which class owns loading; (b) the access pattern; (c) validation/halt semantics; (d) hot-reload scope — before the first `.tres` is authored at task 1-10.

### Current State

- No `src/` config code or `.tres` files exist yet; `design/gdd/game-config.md` (authoritative) defines Rule 2's nine domains with full field range tables; `design/registry/entities.yaml` pins the nine `.tres` paths; architecture.md §4.3 shows representative fields.
- ADR-0002 is Accepted: config-domain Resource classes live at `src/resources/config/`, authored `.tres` at `res://assets/data/config/` (format 3, `script_class` headers), read only through owning Autoloads — `GameConfig` for config domains.
- Gate-check (task 1-7) confirmed the nine domains are consistent across game-config.md ↔ entities.yaml ↔ ADR-0005; **R2 flagged**: `RivalFaithConfig.aggression_interval_turns` is 6 in game-config.md (authoritative) vs 3 in rival-faith-system.md — ruling deferred to task 1-18, no code impact.

### Constraints

- Autoload order: `GameConfig` must be slot 1 (ADR-0001) so every other system's `_ready()` sees LOADED config (GameConfig Rule 2 / EC-5).
- Mobile target: config values are immutable during a play session on shipped builds; no runtime patches (Rule 4).
- Editor workflow: designers must tune live without restarting (Rule 5) — but export builds must not ship a file watcher (AC-8).
- `entities.yaml` rule: **no code reads `.tres` directly outside the owning Autoload** — `GameConfig` is the ONLY reader of config `.tres`.
- Data lives under `res://assets/data/config/` (GDD-pinned paths), not `src/data/` (ADR-0002).

### Requirements

- Nine domains load on startup; `GameConfig` reaches LOADED before any other Autoload's `_ready()` (AC-1).
- Typed access returns in-range values (AC-2, AC-10).
- Out-of-range values clamp with a warning (AC-3); missing required field / missing file hard-halt with descriptive error (AC-4/5).
- No hardcoded balance values in gameplay code (AC-6 — enforced by static scan REG-3 at 1-14 + control-manifest Forbidden rule 1-16).
- Editor-only hot-reload swaps live values within one frame and emits `config_reloaded` (AC-7); absent from export builds (AC-8).
- Saves never contain config values (AC-9 — deferred to M4 by design, recorded not forgotten).

## Decision

1. **`GameConfig` is the sole config boundary.** The Autoload (slot 1) loads the nine `.tres` files once at `_ready()`, in this fixed order, each into a typed Resource property:

| Domain property | `.tres` path | Resource class |
|-----------------|-------------|----------------|
| `conversion` | `res://assets/data/config/conversion_config.tres` | `ConversionConfig` |
| `traits` | `res://assets/data/config/trait_config.tres` | `TraitConfig` |
| `faith_spread` | `res://assets/data/config/faith_spread_config.tres` | `FaithSpreadConfig` |
| `rival_faith` | `res://assets/data/config/rival_faith_config.tres` | `RivalFaithConfig` |
| `progression` | `res://assets/data/config/progression_config.tres` | `ProgressionConfig` |
| `ui_timing` | `res://assets/data/config/ui_timing_config.tres` | `UITimingConfig` |
| `portraits` | `res://assets/data/config/portrait_config.tres` | `PortraitConfig` |
| `map` | `res://assets/data/config/village_map_config.tres` | `VillageMapConfig` |
| `hud` | `res://assets/data/config/hud_config.tres` | `HUDConfig` |

   All nine ship at MVP — including `faith_spread_config.tres`, which has no MVP consumer, per GameConfig AC-1 and OQ-10 (ship all 9; FaithSpread is a Vertical Slice system but its domain file exists to satisfy the nine-domain contract).

2. **Pull pattern, never push.** Systems call `GameConfig.[domain].[field]` at call time and must not cache values locally (GameConfig Rule 3). `GameConfig` emits no load-complete signal; `config_reloaded` is the only signal and it is editor-only. This is what prevents stale-value bugs and keeps one writer of truth.

3. **Field authority = game-config.md range tables.** The authoritative field set for each domain is the field-ranges table in `design/gdd/game-config.md` (e.g. `ConversionConfig` = `base_success_chance`, `trait_modifier_weight`, `approach_cooldown_turns`, `hard_mode_base_modifier`, `max_approaches_per_npc`). architecture.md §4.3 is a **representative** sample, not authoritative; where its field list differs (ConversionConfig shows additional fields such as `trait_modifier_cap`, `min_success_chance`, belief modifiers, band fractions, repeat penalties), the GDD table wins. The `.tres` files authored at 1-10 implement the GDD tables; any field that must exist in code but is absent from the GDD table is flagged to the designer rather than silently invented. **Flag:** this field-set drift is recorded here and should be reconciled in the GDD at the next balance review.

4. **Validation & clamp on load.** Every field is validated against its GDD min/max. Out-of-range values clamp to the boundary and log `push_warning("GameConfig: [domain].[field] clamped from %s to %s")`. Clamping is per-field (no cross-field relational validation — GameConfig EC-7: e.g. `traits_per_npc_min > traits_per_npc_max` passes individually; consumers clamp on read). Missing **optional** fields fall back to the GDD `Default`; missing **required** fields hard-halt. Cross-field inconsistency in PortraitConfig overlay timings follows the same per-field precedent (EC-9; P&E F4 clamps total lifetime).

5. **Hard-halt semantics.** A missing `.tres` file or a missing required field is a fatal startup error: `push_error` with the exact file path / field name, then halt (EC-1/EC-4, AC-4/5). The game must not run in an unknown tuning state. Unparseable/corrupt `.tres` surfaces the Godot parse error directly (EC-2) — no catch.

6. **Editor-only hot-reload.** In the editor only, `GameConfig` watches its nine paths (via `DirAccess`/`FileSystem` polling or Godot's editor file-system notifications), and on a saved change re-loads and re-validates the affected domain, swaps the values, and emits `config_reloaded(domain_name: String)`. Failed reloads (mid-edit invalid state) log a warning, discard, and retain the last valid domain state; `config_reloaded` is not emitted (EC-8). The watcher + signal handler are excluded from export builds by an `Engine.is_editor_hint()` gate and a build-time stripped code path (AC-8). Systems are discouraged from caching config even with the signal (Rule 3).

7. **No config in saves.** AC-9 is deferred to M4 by design: SaveLoad (ADR-0009) serializes game state only; config is always reloaded from `.tres` at boot. Recorded in the 1-14 coverage audit as deferred.

8. **Single-file authority.** Exactly one `.tres` per domain; no per-level/difficulty override files (Rule 7). Difficulty scaling lives as fields inside domains (`ConversionConfig.hard_mode_base_modifier`).

### Architecture

```
res://assets/data/config/            src/resources/config/          runtime (slot 1)
  conversion_config.tres  ──┐     ConversionConfig  ──┐
  trait_config.tres       ──┤     TraitConfig       ──┤
  faith_spread_config.tres──┤     FaithSpreadConfig ──┤
  rival_faith_config.tres ──┼──►  RivalFaithConfig  ──┼──►  GameConfig (Autoload 1)
  progression_config.tres ──┤     ProgressionConfig ──┤        │ LOADED in _ready()
  ui_timing_config.tres   ──┤     UITimingConfig    ──┤        │ (validate/clamp; hard-halt)
  portrait_config.tres    ──┤     PortraitConfig    ──┤        ▼
  village_map_config.tres ──┤     VillageMapConfig  ──┤   every system: GameConfig.[d].[f]
  hud_config.tres         ──┘     HUDConfig         ──┘   at call time (pull, never cache)
                                                              │ editor only
                                        config_reloaded(domain_name) ──► subscribers (discouraged)
```

### Key Interfaces

```gdscript
# GameConfig (Autoload, slot 1)
signal config_reloaded(domain_name: String)   # editor only — AC-7/8

var conversion: ConversionConfig
var traits: TraitConfig
var faith_spread: FaithSpreadConfig
var rival_faith: RivalFaithConfig
var progression: ProgressionConfig
var ui_timing: UITimingConfig
var portraits: PortraitConfig
var map: VillageMapConfig
var hud: HUDConfig

# Usage (pull pattern — the ONLY sanctioned read path):
#   GameConfig.conversion.base_success_chance
#   GameConfig.rival_faith.aggression_interval_turns
# NEVER: load("res://assets/data/config/...") outside GameConfig (entities.yaml rule)

# Example domain Resource (src/resources/config/rival_faith_config.gd)
class_name RivalFaithConfig extends Resource
@export var aggression_interval_turns: int = 6     # game-config.md authoritative; R2: RFS GDD lists 3 — task 1-18
@export var reharden_strength: float = 1.0
@export var counter_approach_random_weight: float = 0.0
@export var grace_window_turns: int = 2
```

### Implementation Guidelines

- Implement at task 1-10: `src/autoload/game_config.gd`, nine `src/resources/config/*.gd` classes, nine `.tres` (format 3, `script_class` headers) authored from the GDD field-range tables.
- Validation tables (min/max/default/required per field) come from `design/gdd/game-config.md` — do not invent ranges; if a field is missing from the GDD table, flag it (see Decision 3).
- Each Resource declares `@export` fields with GDD defaults so `.tres` authoring is inspectable.
- `Engine.is_editor_hint()` gates the watcher; export builds strip the watcher + `config_reloaded` handler (AC-8, verified at 1-10 GCF-7).
- Ordering: load all nine in the fixed table order; the first failure hard-halts with the exact path/field.
- `Godot --headless` boot must remain exit 0 with the nine `.tres` present (1-10 tests GCF-1..8).

## Alternatives Considered

### Alternative 1: Per-system config files read directly by each system

- **Description**: Each consuming system `load()`s its own `.tres`.
- **Pros**: No central class; systems self-contained.
- **Cons**: Violates the entities.yaml owning-Autoload rule; multiple readers of one file → inconsistent/cached copies; no single validation point; hard-halt semantics duplicated per system.
- **Estimated Effort**: Lower initially, higher to keep consistent.
- **Rejection Reason**: The GDD mandates one `GameConfig` Autoload; the pull pattern and single-reader rule exist precisely to prevent drift and stale caching.

### Alternative 2: Global static config class (no Autoload)

- **Description**: A `class_name GameConfig` with static vars loaded by an explicit init call.
- **Pros**: No Autoload registration; testable statics.
- **Cons**: Breaks ADR-0001's slot-1 ordering guarantee (nobody forces init before other `_ready()`s); static state is less inspectable in the editor; GDD mandates "Autoload singleton".
- **Estimated Effort**: Similar.
- **Rejection Reason**: The GDD explicitly requires an Autoload listed first; the slot-1 order is the mechanism that makes AC-1 (LOADED before other `_ready()`s) hold.

## Consequences

### Positive

- One reader, one authority: every tuning value has a named home, range, and file — designer-tunable without code changes.
- Pull pattern prevents stale cached values; validation prevents out-of-range corruption; hard-halt prevents silent unknown-state boots.
- Nine-domain contract matches AC-1/AC-10 and unblocks all downstream M1..M6 systems that read config.
- Editor hot-reload keeps the tuning loop live without breaking export builds.

### Negative

- Startup is fail-fast: a single broken `.tres` blocks the whole game (accepted — unknown tuning state is worse).
- No cross-field relational validation at MVP (EC-7) — consumers must clamp relations themselves.
- The field-set drift between architecture.md §4.3 and the GDD tables (ConversionConfig) must be reconciled; GDD tables are authoritative (flagged above).

### Neutral

- `config_reloaded` exists but subscribers are discouraged (pull pattern); it is mostly a debug/design affordance.
- `faith_spread_config.tres` ships with no consumer until Vertical Slice (OQ-10 — intentional).
- AC-9 (no config in saves) is deferred to M4 by design and tracked in the coverage audit.

## Addendum 1 — Dialogue Authoring Format (DCD OQ-3 / architecture.md OQ-5)

**Date:** 2026-08-18 (Sprint 1 task 1-20 · tools-programmer + narrative-director)
**Status:** Accepted — resolves DCD OQ-3, architecture.md §9 OQ-5, and the TR-DCD-013 `schema_version` pipeline contract.

### Context

Dialogue content ships at runtime as `res://assets/data/dialogue/dialogue_database.tres` (DCD AC-2; ADR-0002 format 3), loaded by the `DialogueDatabase` Autoload — but authoring dialogue directly in `.tres` is impractical for writers (DCD OQ-3). Story 1-12 produced the 100-string scaffold via a throwaway script (`/tmp/gen_dialogue_tres.gd`, deliberately not committed) to prove the runtime shape; that is not a repeatable authoring path. M5 needs full content volume (100+ strings, growing) authored and validated by writers, not engineers.

### Decision

1. **Source format: YAML (`dialogue_content.yaml`), one canonical file committed to the repo.** Chosen over CSV/JSON/Sheets because dialogue is nested (per-approach pools, per-approach×outcome summaries, per-archetype flavour) and needs writer comments, multi-line strings, and diff-friendly review. YAML handles all four natively; CSV's delimiter/quote escaping grows with every comma or newline in a line of dialogue; JSON has no comments and is noisy for writers; a live external service as the single source of truth adds a network dependency and no git history.
2. **Runtime format unchanged: `.tres`.** The engine keeps loading `dialogue_database.tres`; the `DialogueDatabase` API and the ADR-0002 data model are untouched. This pipeline is authoring-side only.
3. **Conversion pipeline: standalone script (Python), not a Godot import plugin.** Three stages:
   `dialogue_content.yaml → validator → .tres emitter → dialogue_database.tres`
   - Hosted at `tools/dialogue/` (repo convention: authoring/build tooling lives outside `res://` so Godot never imports the source file; CI-gates the pipeline once story 1-21 lands).
   - **Validator** enforces the DCD content rules the runtime cannot: EC-1 under-filled slots (<3 lines → hard error), EC-3 duplicate-line detection, EC-5 localisation completeness, EC-7 proper-noun scan (authoring-time Approach Purity Test), EC-11 slot-level tense tags, R8 `V_total` audit — plus schema validation (unknown keys, wrong types) before emitting.
   - **Emitter** writes format-3 `.tres` with `script_class` headers and per-archetype `NPCFlavourData` sub-resources, exactly matching the 1-12 output shape; it also stamps **`schema_version` (TR-DCD-013)** — the converter carries a schema version, bumps it on structural change, and the runtime load-time check (DCD OQ-1 recommendation) can then migrate.
4. **Google Sheets stays a writer convenience, never a source of truth.** Sheets → export CSV → small adapter → YAML keeps the repo file canonical; the pipeline itself has zero external-service dependency.
5. **Backfill.** The 1-12 scaffold `.tres` remains the shipped artifact until M5. The M5 content-authoring task regenerates it through this pipeline (author YAML from the current scaffold, re-emit, diff) so source and runtime can never drift.

### Authoring Workflow (M5-ready)

1. Writer edits `assets/data/dialogue/dialogue_content.yaml` (or a Sheets row set) — one entry per line, keyed by pool/approach/outcome/archetype.
2. Run `tools/dialogue/convert.py` (validator + emitter in one command; usage documented in `tools/dialogue/README.md`).
3. Validator errors (duplicates, under-filled slots, proper nouns, tense-tag drift, V_total mismatch) fail the run with the offending key named — no load-time warnings surface in the shipped build.
4. Emitter rewrites `dialogue_database.tres`; `git diff` shows a reviewable content change; CI (story 1-21) re-runs the validator + full GUT suite so the runtime audit (R8 / DCD AC-10..13) still passes.
5. Commit the YAML source and the regenerated `.tres` together — the `.tres` is a checked-in build artifact for runtime parity; the YAML is the authoring source.

### Alternatives Considered

| Option | Pros | Cons | Decision |
|--------|------|------|----------|
| **YAML (chosen)** | Nested, comments, multi-line, diff-friendly, Sheets-exportable via adapter | Indentation-sensitive; needs a parser outside the engine (Python/PyYAML) | ✓ |
| CSV | Universal; spreadsheet-native; trivial parser | Delimiter/quote escaping for dialogue text; flat only; no comments; merge-conflict prone | Rejected |
| JSON | Universal; strict | No comments; noisy for writers; hand-editing awkward | Rejected |
| Google Sheets as source | Familiar to writers; live edits | External service dependency; no git history; offline breaks pipeline | Rejected (adapter only) |
| Author directly in `.tres` | Zero pipeline | The problem we are solving; writers cannot realistically maintain format-3 text | Rejected |
| Godot import plugin | In-editor refresh | Parser addon dependency; editor-only; harder to CI-gate; import order side effects | Rejected (standalone script preferred) |

### Consequences

**Positive**
- Writers author in a human format with comments and multi-line strings; engineers keep a typed, stable runtime Resource.
- All DCD content rules become build-time failures instead of load-time warnings (EC-1..EC-11, R8) — the runtime keeps only its defensive checks.
- No runtime change: `DialogueDatabase`/ADR-0002 model untouched; the entities.yaml owning-Autoload rule is unaffected (this is build-time tooling, not a runtime `.tres` reader).

**Negative**
- YAML indentation errors are the main writer-facing risk — mitigated by validator diagnostics naming the file/line/key.
- The 1-12 scaffold `.tres` has no committed source until the M5 backfill (accepted, recorded — story 1-12 note).

**Neutral**
- Adds a repo-level tool dependency (Python + PyYAML) used only at authoring/CI time; the game itself never runs it.

5. **Drift flag status: CLOSED.** The flag text in Decision 3 remains as the historical record (do not delete); this addendum is the closure record. The CLE (2-7) reads every field at call time (pull pattern, AC-8.4 test proves no caching) — it has no legacy to migrate.
