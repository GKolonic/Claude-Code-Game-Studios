## Summary

M2's determinism requirements (NPC CS AC-1 same-seed village generation, CLE AC-1 pure/seeded resolve, Trait Assignment Formula weighted draw without replacement) cannot be met with Godot's global `randf()`/`randi()` generator. This ADR pins one strategy: `VillageDefinition.rng_seed` seeds village generation through a single RNG abstraction (`src/systems/npc/rng_helpers.gd`), the CLE draws exactly one uniform roll from a per-call seeded source, runtime RNG is NOT persisted at MVP (architecture OQ-7 — the full persistence ruling is deferred to ADR-0009 at M4), and `trait_revealed` ships with zero MVP subscribers (OQ-8).

## Context

### Problem Statement

M2 introduces three RNG consumers with strict determinism requirements:

- **NPC CS AC-1** — `initialize_village()` on the same `VillageDefinition` must produce identical NPCs (traits, belief states, connections) on every run: the seeded trait draw is what makes village data reproducible for tests, debugging, and the golden fixture (2-14).
- **Trait Assignment Formula** (NPC Trait Database GDD, TR-TDB-006/010) — rarity-weighted random draw **without replacement** on the 16-trait pool; no NPC may receive duplicate trait IDs.
- **CLE AC-1 / AC-6** — `resolve()` is a pure function and draws exactly one uniform roll; outcome zones are derived from that roll with strict-`<` boundaries, and the empirical distribution must match the formula bands within ±3% over large seeded runs.

Godot's bare `randf()`/`randi()` read global generator state seeded once by `randomize()` at startup — not reproducible, not per-call-site seedable, and shared across all callers. Without a decision now, 2-5/2-6/2-7 would each invent their own RNG handling, and the AC-1 determinism guarantee would silently not hold. The cost of not deciding: unreproducible tests, undebuggable generation, and a broken milestone outcome.

### Current State

- No RNG code exists yet — `src/systems/npc/` is empty; architecture §7 pins the ownership path `src/systems/npc/rng_helpers.gd`.
- `VillageDefinition` is Approved with `rng_seed: int` (ADR-0002, confirmed 2026-08-18); `village_01.tres` (2-4) will carry a fixed seed.
- TR-TDB-006 and TR-TDB-010 are `active` — the 1-17 architecture review recorded them as "resolved-by design at M2" (via this ADR), matching the M2 milestone statement.
- GameConfig pull pattern is established (ADR-0005): the CLE reads `GameConfig.conversion.*` at call time; no caching.

### Constraints

- **Engine-version sensitivity**: Godot `RandomNumberGenerator` produces different streams across engine versions (implementation is not frozen). Determinism is therefore defined as a **same-engine-version contract** (R16), pinned here to 4.6.stable.official.89cea1439.
- **No persistence at MVP**: save/load does not exist until M4 (OQ-7) — nothing can serialize RNG state, and no cross-session replay is expected.
- **No global/shared mutable RNG state**: two M3 callers (DCS, RFS) plus tests must not interfere; the ADR-0001 Autoload singletons (NPCRegistry, CLE) must not hold mutable RNG as member state that breaks purity/reproducibility.
- **Mobile target**: RNG is used only at event boundaries (village generation, per-conversion resolve) — never per-frame; cost must stay trivial.
- **Formatting constraints from GDDs**: Trait Assignment Formula Step 3 (weighted draw, pool erase), NPC CS Rule 8 (generation order), CLE Formulas 4–5 (single roll, strict-`<` zones).

### Requirements

- R1. TR-TDB-006: rarity-weighted random draw without replacement (60/30/10 trait pool bands) — reproducible from a seed.
- R2. TR-TDB-010: no duplicate trait IDs per NPC — structurally guaranteed by draw-without-replacement.
- R3. NPC CS AC-1: same seed → identical village generation (two `initialize_village()` calls byte-identical).
- R4. NPC CS AC-4: statistical separation — Widow `bereaved` rate > Soldier rate across 100 seeded villages.
- R5. CLE AC-1: `resolve()` pure — no state written to NPCRegistry/GameConfig; same inputs + same roll ⇒ same outcome.
- R6. CLE AC-6: single uniform roll per resolve; strict-`<` zone resolution; 10,000-roll distribution within ±3% of band fractions.
- R7. OQ-7 ruling: runtime RNG state is **not** persisted at MVP; the full persistence decision is deferred to ADR-0009 (M4) — recorded here, not forgotten.
- R8. OQ-8 ruling: `trait_revealed` emission ships with **zero MVP subscribers** (debug/audio are prospective post-MVP consumers).

## Decision

1. **Seeded village generation via `VillageDefinition.rng_seed`.** `NPCRegistry.initialize_village()` creates its generation RNG through the abstraction (Decision 2) seeded from `village_definition.rng_seed` (a fixed authored int, e.g. `village_01` pins one in its `.tres`). One seed per village, one RNG stream per generation pass; every draw in generation (trait assignment, connection/materialization order per NPC CS Rule 8, any stochastic belief seeding) consumes that stream in a fixed, documented order. Same seed + same data + same engine version ⇒ identical village, every time.

2. **RNG abstraction ownership — `src/systems/npc/rng_helpers.gd`.** All determinism-critical RNG lives in a single plain class (`class_name RNGHelpers`, architecture §7): the seeded `RandomNumberGenerator` factory, `random_int_inclusive(min, max)`, `weighted_random_choice` + pool erase (Trait Assignment Formula Step 3, TR-TDB-006), and the CLE uniform-roll source. Helpers are static and take the `RandomNumberGenerator` instance as the first parameter — **no global/shared mutable state anywhere**. Each caller owns (or threads) its RNG instance:
   - NPCRegistry: one generation RNG per `initialize_village()` call, seeded from `rng_seed`, dropped at end of generation.
   - CLE: a per-`resolve()` RNG passed by the caller (M3 callers DCS/RFS own a session RNG) — or, on the nullable default path, a fresh non-deterministic RNG (acceptable at MVP per Decision 4).
   - Tests: always explicit seeds.

3. **CLE single-roll sourcing.** `resolve()` draws exactly one uniform float from the RNG abstraction's roll source (`[0.0, 1.0)`, strict-`<` zones per CLE Formula 5: `roll < P_final → PERSUADED; < P_final + P_softened → SOFTENED; < P_final + P_softened + P_resisted → RESISTED; else HARDENED`). The roll is the only randomness in a resolve; everything else is derived deterministically from GameConfig pull reads and NPCRegistry state at call time (ADR-0005 pull pattern; CLE AC-8.4 proves no caching). `resolve()` writes nothing to NPCRegistry/GameConfig (CLE AC-1 pure-function contract).

4. **Non-persisted runtime RNG at MVP (OQ-7 resolution).** Runtime RNG **is not persisted** at MVP: restored sessions get fresh randomness; there is no save/replay determinism contract. This position is recorded here and the full persistence ruling (whether to persist RNG state or re-derive from village seeds at M4) is **deferred to ADR-0009** — not silently dropped.

5. **`trait_revealed` ships with no MVP consumers (OQ-8 resolution).** NPCRegistry emits `trait_revealed` as part of its reveal API contract; nothing subscribes at MVP (debug/audio are prospective post-MVP consumers). AC-15 tests the no-op path (a no-op reveal emits no signal). No dead-code cleanup of the emission without Creative Director say-so (R17).

6. **Same-engine-version determinism contract (R16 mitigation).** Determinism guarantees made here are scoped to the pinned engine (4.6.stable.official.89cea1439). A future engine upgrade re-runs 2-5 RG-1, 2-6 AC-1, 2-7 AC-6.x and the 2-14 golden fixture before determinism is re-claimed; cross-platform (Linux dev vs Android device) re-verification happens at M7 per R16.

7. **TR closure note.** TR-TDB-006 and TR-TDB-010 are **resolved-by-design at this ADR**: the implementation detail lands in `rng_helpers.gd` (2-5, weighted draw + no-duplicate guarantee) and NPCRegistry (2-6, AC-1/AC-4/AC-5). Their registry status flips from `active` to the review's partial-TR/closure notes at 2-10 (M2-scoped architecture review) once the acceptance tests pass.

### Implementation Guidelines

- Implement the abstraction at 2-5; `rng_helpers.gd` is the ONLY file that constructs `RandomNumberGenerator` (except entropy fallback in CLE's null path, which may call `randi()`/`Time.get_ticks_usec()` for a runtime-only seed — never for tests).
- Generation order within `initialize_village()` is part of the determinism contract: document the exact draw order in the 2-6 implementation; the golden fixture (2-14) freezes it.
- Statistical tests (2-5 RG-3, 2-6 AC-4, 2-7 AC-6.x) use explicit seeds and bounded draws (≤ 10,000 per run) so suite time stays under ~2 min (QA plan OQ-QA1).
- Do not use `randomize()`; do not store RNG instances on Autoloads (purity/reproducibility); tests must never read global RNG.
- `weighted_random_choice` must normalize weights and handle a zero-sum pool (warn + uniform fallback) — an empty pool is a programmer error (assert/warn, return `{}`).

## Alternatives Considered

### Alternative 1: Global `randf()`/`randi()` with `randomize()` at startup

- **Description**: Use Godot's global generator everywhere; seed once at boot.
- **Pros**: Zero abstraction; standard Godot-idiomatic code.
- **Cons**: Not reproducible (seed is time/entropy-based); no per-call-site seeding → AC-1, TR-TDB-006/010, CLE AC-6.x all untestable; shared global state across callers; debug replay impossible.
- **Estimated Effort**: Lowest.
- **Rejection Reason**: Violates every M2 determinism requirement; the milestone's headline outcome (NPC AC-1 seeded determinism) would be unprovable.

### Alternative 2: Persist RNG state (or seeds) in saves at MVP

- **Description**: Serialize RNG state/seed per session so restored sessions replay identical randomness.
- **Pros**: Save/replay determinism; identical dev-vs-restore behavior.
- **Cons**: Save/load does not exist until M4 (ADR-0009); would force schema churn now; runtime RNG at MVP is ephemeral per-session state with no replay consumer; OQ-7's proposed position (accept fresh randomness at MVP) is already Creative Director-approved (decision #3).
- **Estimated Effort**: Higher (persistence schema + state restore rules before they are designed).
- **Rejection Reason**: Premature — the full persistence ruling belongs to ADR-0009 (M4); this ADR records the MVP non-persistence position and defers, rather than half-implements, persistence.

### Alternative 3: Custom deterministic PRNG (e.g. xorshift/LCG class) for cross-version stability

- **Description**: Ship a hand-rolled PRNG so streams are stable across engine versions and platforms.
- **Pros**: Version-independent determinism; full control of stream quality.
- **Cons**: Third-party-free but bespoke crypto-adjacent code = maintenance + review cost; unnecessary at MVP because the engine's `RandomNumberGenerator` is stable within the pinned version and runtime RNG is not persisted (Decision 4) — cross-version replay is not an M2 contract; R16's mitigation is the same-version contract + re-verification, not a new PRNG.
- **Estimated Effort**: Medium-high (implement, test quality, maintain).
- **Rejection Reason**: Premature complexity; revisit only if R16 escalates at M7 (device divergence) or if M4 persistence requires cross-version replay streams.

## Consequences

### Positive

- NPC AC-1 determinism is provable: same seed ⇒ identical village, testable and debug-reproducible.
- TR-TDB-006/010 trace to one owned implementation (`rng_helpers.gd`) with a structural no-duplicate guarantee.
- CLE stays pure (AC-1): one roll in, deterministic outcome out; the abstraction is the only RNG seam — swappable without touching formula code.
- Tests get full isolation: no global RNG state, no cross-test interference.
- OQ-7/OQ-8 are ruled and recorded — 2-5/2-6/2-7 implement one strategy, not three guesses.

### Negative

- Determinism is a **same-engine-version contract** — an engine upgrade invalidates the guarantee until the determinism suites re-pass (R16; explicit re-verification path).
- No save/replay determinism at MVP — restored sessions differ in rolls (accepted per OQ-7; M4 ADR-0009 decides the real ruling).
- `trait_revealed` emission ships with zero subscribers (OQ-8) — "emits into the void" until a debug/audio consumer exists (R17).

### Neutral

- Every RNG call site now threads an explicit instance — slightly more verbose than global access, but self-documenting.
- The golden fixture (2-14) becomes the long-term sentinel: any formula/weight/catalogue drift that alters generation shows up as fixture diff.

## Migration Plan

No migration — no RNG code exists before this ADR. Forward-compatibility seam: all consumers already target the `RNGHelpers` API, so if ADR-0009 (M4) or an engine upgrade changes the strategy (persistence, custom PRNG), only `rng_helpers.gd` internals change; the 2-5 RG-1, 2-6 AC-1, 2-7 AC-6.x and 2-14 golden-fixture suites must pass unchanged.

1. 2-5 implements `rng_helpers.gd` per the Key Interfaces above.
2. 2-6 threads generation RNG from `village_def.rng_seed`; 2-7 threads per-resolve RNG.
3. 2-14 freezes the golden fixture so future drift is caught.

**Rollback plan**: Revert to global `randf()` only if the abstraction fails at runtime — this loses all determinism guarantees and is therefore not a preferred path; any rollback requires a new ADR/decision.
