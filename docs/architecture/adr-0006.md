# ADR-0006: Input Architecture (MTF Sole Input Boundary, dp Conversion, 44dp Floor, Blocking-Layer Ownership, R3 Priority Decision)

## Status

Accepted — 2026-08-11 (Sprint 1 task 1-9; Creative Director delegation per OQ-6: ADR written at Sprint 1 start and Accepted before 1-13 begins)

## Summary

The Mobile Touch Framework (MTF) Autoload is the **sole input boundary**: no UI code reads `Input` directly, all touch flows through MTF's `_input()` handler, registered-target hit-testing, and gesture signals. MTF owns dp conversion (`pixels_per_dp`), enforces the 44dp minimum tap-target floor, and is the only system allowed to manage blocking layers (owner: Conversion UI). R3 is recorded with its chosen mitigation: MTF uses registry-based hit-testing and never calls `set_input_as_handled()` unless a registered target consumed the event, so Godot's reverse-scene-order `_input()` propagation cannot starve other consumers.

## Context

### Problem Statement

Fourteen MVP systems touch the input path; the MTF GDD mandates MTF as the input boundary (Rules 1/9) and the Conversion UI as the only blocking-layer owner (Conversion UI Rule 2). Without an explicit input architecture, three failure modes are likely: (a) UI nodes read `Input` directly, bypassing gesture classification and the 44dp floor; (b) multiple systems call `set_input_as_handled()`, starving other consumers; (c) the blocking-layer stack gets a second owner, breaking modal ordering during conversations. Additionally, the MTF GDD Rule 1 claims that listing MTF "first" in Project Settings guarantees input priority — **that claim needs verification against Godot 4.6's actual `_input()` propagation order (architecture risk R3)**.

### Current State

- No input code exists yet (M0 shipped stub Autoloads only); task 1-13 will implement MTF.
- MTF GDD Rule 1: MTF reads `_input()`, not `_unhandled_input()`, so Controls cannot silently consume before MTF sees events; Rule 15 pins 15 non-overridable constants including `TAP_TARGET_MIN_SIZE_DP = 44`; F-1 defines dp conversion with a 160-DPI fallback; AC-1..14 pin gesture behaviour; blocking-layer stack (Rule 9) with priority tiers; haptic on tap only (Rule 12).
- ADR-0001 orders MTF at slot 4 (after GameConfig/TraitDatabase/DialogueDatabase, before all UI-adjacent Autoloads). ADR-0003 pins the MTF signal surface (`tapped`, `long_press_started`, `long_press_released`, `swiped`, `touch_cancelled`) and the single blocking-layer-owner rule.
- **R3 finding (recorded)**: Godot's `_input()` propagates in **reverse scene order** — the last Autoload in `project.godot` receives the event first. MTF at slot 4 therefore receives events *after* slots 5–10, not "first" as the GDD's Rule 1 wording claims. The claim "listed first to guarantee input processing priority" is **wrong** for raw `_input()` ordering (MTF's slot-4 registration does not give it priority over later slots).
- Safe-area finding (task 1-2, session state): `DisplayServer.get_display_safe_area() -> Rect2i` (no params) verified on 4.6; interactive controls should render inside it. MTF hit-testing operates in screen coordinates; UI layout uses the safe area for placement, but hit-test rects are the registered Controls' rects — the safe area constrains *where* targets are placed, not the hit-test algorithm itself.

### Constraints

- UI must never read `Input` directly (control-manifest Forbidden rule; MTF GDD Rules 1/9; ADR-0003).
- `_input()` propagation order is engine-fixed: reverse scene order (verified behaviour; see Decision 4).
- CanvasLayer `layer` values are rendering-only — never input-priority discriminators (MTF GDD Rule 9; ADR-0004).
- 44dp is a hard floor (iOS HIG / Android Material minimum; MTF Rule 15 `TAP_TARGET_MIN_SIZE_DP`; do not lower).
- Haptic: framework-level tap-only, 80ms pulse (MTF Rule 12).
- Recursive Control disable (Godot 4.5+) is used by blocking layers to stop `_gui_input()` consumption — verify availability on 4.6 at 1-13 (MTF GDD Dependencies).
- Mobile target: single-finger at MVP (`SINGLE_FINGER_MODE = true`).

### Requirements

- Exactly one input boundary: MTF. All touch gestures flow through MTF's `_input()`; UI registers targets and consumes signals.
- dp conversion is MTF-owned: `pixels_per_dp` read-only, computed once from `DisplayServer.screen_get_dpi()` with 160 fallback (F-1, AC-12/13).
- 44dp minimum tap target enforced at hit-test time via center-anchored rect inflation (F-2, AC-3).
- Blocking-layer stack with priority tiers; **Conversion UI is the only owner** (ADR-0003/4, Conversion UI Rule 2).
- Haptic on confirmed Tap only (80ms); no framework visual feedback (Rule 12/14, AC-14).
- `set_input_as_handled()` only when a registered target consumed the event (R3 mitigation, MTF GDD Rule 1).
- Gesture constants stay compile-time at MVP (MTF Rule 15; promotion to GameConfig post-MVP if live tuning is needed — ADR-0005).

## Decision

1. **MTF is the sole input boundary.** All touch input is consumed in `MobileTouchFramework._input()`. No UI node, scene, or Autoload reads `Input`, `InputEventScreenTouch`, `InputEventScreenDrag`, or calls `set_input_as_handled()` except MTF (and MTF only when a registered target consumed the event — see Decision 4). This is enforced by code review + the control-manifest Forbidden rule (task 1-16) and verified by a static scan at 1-13 (MTF-15).

2. **dp conversion is MTF-owned.** `pixels_per_dp: float` is computed once at startup from `DisplayServer.screen_get_dpi()`: `pixels_per_dp = clamp(dpi, 72, 640) / 160.0`, falling back to 1.0 (160 DPI) when `dpi <= 0` or implausible, with a warning (F-1, EC-3, AC-12). All design values (44dp, 8dp, 40dp, 150dp/s) are expressed in dp; consumers never do pixel math for sizing or hit-testing (Rule 11). Hit-testing uses registered Controls' rects in screen pixels; the safe-area finding (task 1-2) governs layout placement only, not hit-test geometry.

3. **44dp floor + gesture constants are compile-time.** `TAP_TARGET_MIN_SIZE_DP = 44`; targets below 44×44dp get center-anchored rect inflation at registration (F-2) with a debug warning naming the node (EC-6, AC-3). All 15 GDD constants (Rule 15) ship as constants; no GameConfig dependency at MVP. If any constant needs live tuning post-MVP, promote it to a GameConfig entry per ADR-0005.

4. **R3 decision — registry-based hit-testing + no `set_input_as_handled()` unless consumed.** Godot's `_input()` propagates in **reverse scene order** (last Autoload first). MTF at slot 4 (ADR-0001) does **not** receive events first. Chosen mitigation (three parts):
   - **Registry-based hit-testing**: MTF does not rely on event-order priority to claim events. Every registered Control is in a priority-sorted registry; on each touch event, MTF hit-tests the registry and routes gestures to the correct target *by geometry and priority tier* — independent of who saw the event first.
   - **No `set_input_as_handled()` unless consumed**: MTF calls `set_input_as_handled()` **only** when a registered target consumed the event (a tap resolved to a target, a gesture completed to a registered area). For misses, dead-band, multi-finger discards, and unregistered input, MTF leaves the event unhandled — so later consumers (e.g. future pause-menu, OS UI) still receive it. This makes the reverse-order claim moot for MTF's core path: MTF sees every event regardless of order, and it only marks events handled when it actually produced a gesture.
   - **`process_priority` as a backstop**: if a specific platform/device shows another Autoload (or a Control's `_gui_input()`) consuming touch events before MTF can classify them, set MTF's `process_priority` high (low value) on the Autoload node — recorded as a runtime fallback, not the primary mechanism. Verified at 1-13 with synthetic InputEvents (MTF-1..13) and at M5/M6 with real scenes.

   The MTF GDD Rule 1 wording ("listed first to guarantee input processing priority") is **amended by this ADR**: slot 4 guarantees MTF exists before UI registers (ADR-0001), but raw input priority comes from the registry hit-test + consume-only marking, not from listing order. A one-line wording update to the MTF GDD is flagged for the consistency review (task 1-18 window / next GDD review pass).

5. **Blocking-layer ownership: Conversion UI only.** `push_blocking_layer(id)` / `pop_blocking_layer(id)` / `clear_blocking_layers()` are exposed by MTF (Rule 9); the Conversion UI is the **only** caller while a conversation session is open (ADR-0003, Conversion UI Rule 2). While a blocking layer is active, registered areas below the layer's tier receive no signals; for UI subtrees, Godot 4.5+ Recursive Control disable prevents `_gui_input()` consumption. Any second owner is a review failure (guardrail; verified MTF-9).

6. **Haptic on tap only.** MTF emits an 80ms `Input.vibrate_handheld()` pulse on every confirmed Tap (Rule 12). Long press, swipe, and cancellation emit no framework haptic. No visual feedback at the framework level — ever (Rule 12/14, AC-14; consuming systems own all visual response).

7. **Gesture classification per GDD.** Tap ≤350ms/≤8dp; long press ≥600ms; swipe ≥40dp + ≥150dp/s (45° sectors); dead band 350–600ms emits nothing; 800ms timeout → `touch_cancelled`; 100ms debounce ±10dp; single-finger only (Rules 3–8, 13–15; F-3/F-4/F-5). State machine per the GDD §States and Transitions. All verified via synthetic InputEvents at 1-13 (AC-1..13).

### Architecture

```
All touch (InputEventScreenTouch / InputEventScreenDrag)
        │
        ▼
MobileTouchFramework._input()   ← sole boundary; reverse-scene-order safe
  ├─ finger_index filter (SINGLE_FINGER_MODE)
  ├─ debounce gate (100ms ±10dp) ──► discard
  ├─ gesture state machine (IDLE → TOUCH_DOWN → LONG_PRESS_PENDING /
  │    SWIPE_TRACKING → RESOLVING)
  ├─ blocking-layer tier check (Conversion UI owns the stack)
  ├─ priority-sorted registry hit-test (44dp-inflated rects)
  │     └─ if consumed → emit tapped/long_press_*/swiped + haptic(tap only)
  │                       + set_input_as_handled()  [R3: only when consumed]
  └─ miss / dead-band / multi-finger → no signal, no handled-mark

pixels_per_dp = clamp(DisplayServer.screen_get_dpi(), 72, 640) / 160.0  (fallback 1.0)

Signals: tapped(target, pos) · long_press_started(target, pos) ·
         long_press_released(target, pos) · swiped(dir, delta, velocity) ·
         touch_cancelled()
```

### Key Interfaces

```gdscript
# MobileTouchFramework (Autoload, slot 4)
signal tapped(target: Control, position: Vector2)
signal long_press_started(target: Control, position: Vector2)
signal long_press_released(target: Control, position: Vector2)
signal swiped(direction: GameEnums.SwipeDirection, delta: Vector2, velocity: Vector2)
signal touch_cancelled()

var pixels_per_dp: float              # read-only, cached at startup

func register(control: Control, priority: int) -> void   # must be called in _ready()
func unregister(control: Control) -> void                # must be called on tree_exiting
func push_blocking_layer(layer_id: StringName) -> void   # Conversion UI ONLY (ADR-0003)
func pop_blocking_layer(layer_id: StringName) -> void
func clear_blocking_layers() -> void                     # e.g. on window focus loss (EC-7)

# R3 mitigation contract:
#   - hit-test the priority registry, never rely on event arrival order
#   - call set_input_as_handled() ONLY when a registered target consumed the event
```

### Implementation Guidelines

- Implement at task 1-13: `src/autoload/mobile_touch_framework.gd`, gesture state machine, priority registry, blocking-layer stack, dp conversion, constants per MTF Rule 15.
- Tests use **synthetic InputEvents** (`Input.parse_input_event` with constructed `InputEventScreenTouch`/`InputEventScreenDrag`) per QA plan OQ-A; MTF-1..16 cover AC-1..14 + sole-boundary scan + handled-mark rule.
- Registration contract: consumers call `register()` in `_ready()` and `unregister()` on `tree_exiting` (MTF GDD consuming-system contract).
- Safe area: use `DisplayServer.get_display_safe_area()` (verified 4.6, task 1-2) for *layout* placement of interactive zones; hit-test rects are the registered Controls' rects. `get_display_cutouts()` (Android) available as bonus evidence.
- Verify Godot 4.5+ Recursive Control disable availability on 4.6 at 1-13 (flagged in MTF GDD Dependencies).
- `pixels_per_dp` must be readable by any consumer but computed once; never re-queried per frame (Rule 10).
- Do not add visual feedback in MTF (AC-14) and do not add haptic beyond tap (Rule 12).

## Alternatives Considered

### Alternative 1: `_unhandled_input()` for MTF

- **Description**: Read events in `_unhandled_input()` so Controls get first pass via `_gui_input()`.
- **Pros**: Control-native handling runs first; fewer consumed-state conflicts.
- **Cons**: Violates MTF GDD Rule 1 ("`_input()` — not `_unhandled_input()`"); Controls could consume events MTF needs to classify (e.g. swipe from a button); blocking-layer Recursive disable becomes mandatory to stop `_gui_input()` even for background gestures.
- **Estimated Effort**: Similar.
- **Rejection Reason**: The GDD pins `_input()`; MTF must see every raw event to enforce gesture classification and the 44dp floor globally, regardless of Control focus.

### Alternative 2: Rely on autoload listing order for input priority

- **Description**: Keep the GDD's "listed first" claim; assume slot 4 gives MTF priority.
- **Pros**: No extra machinery; matches the GDD's Rule 1 wording.
- **Cons**: **Empirically wrong on Godot 4.x** — `_input()` propagates in reverse scene order; slot 4 receives events after slots 5–10. A later Autoload calling `set_input_as_handled()` would starve MTF; silent, order-dependent input bugs.
- **Estimated Effort**: Zero up front, high in debugging.
- **Rejection Reason**: Directly contradicts the engine's documented propagation order; the R3 risk exists precisely because this claim was unverified.

### Alternative 3: Event-bus input router

- **Description**: A separate input router Autoload that all systems subscribe to for raw events.
- **Pros**: Centralized raw-event distribution.
- **Cons**: Duplicates MTF's already-mandated boundary; adds an 11th Autoload the GDDs don't require; two layers to reason about.
- **Estimated Effort**: Higher.
- **Rejection Reason**: MTF *is* the router per the GDD; adding another layer violates separation of concerns (same reasoning as ADR-0003's event-bus rejection).

## Consequences

### Positive

- One enforceable input path: UI never reads `Input`; all gestures, dp math, and the 44dp floor live in one class (verified by static scan MTF-15).
- R3 is resolved with a concrete mitigation that is robust to engine event order; `set_input_as_handled()` discipline prevents consumer starvation.
- Blocking-layer ownership is unambiguous (Conversion UI only), preventing modal-stack conflicts.
- Haptic/visual separation: framework tap-only haptic; all visual feedback owned by consumers (art-directed).

### Negative

- MTF's GDD Rule 1 wording is now technically inaccurate ("listed first…guarantee input processing priority") — amended by this ADR; a one-line GDD wording update is flagged for the next consistency pass.
- All UI must go through MTF registration — an up-front discipline cost (consumers must `register()`/`unregister()` at the right lifecycle points).
- Registry-based hit-testing adds a small per-event cost (bounded: max 32 registered areas, Rule 10).

### Neutral

- CanvasLayer values remain rendering-only; input priority is orthogonal (ADR-0004).
- Gesture constants are compile-time at MVP; post-MVP promotion to GameConfig is possible via ADR-0005.
- Safe-area data is available for layout but does not alter hit-test geometry.
