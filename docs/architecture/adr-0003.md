# ADR-0003: Signal Architecture & Communication Discipline

## Status

Accepted — 2026-08-09 (M0 foundation; approved by Creative Director)

## Summary

All cross-system communication between orchestration layers is **signal-only** where the GDDs
mandate it — GSM↔DCS, VMV→DCS, HUD→gameplay — with a short, enumerated list of command edges.
MTF is the **sole input boundary** (register/unregister + blocking layers) and the Conversion UI
is the **only** blocking-layer owner.

## Context

### Problem Statement

With ten Autoloads and four scenes, the failure mode to avoid is spaghetti coupling: systems
calling each other's methods from `_ready()`, UI reading gameplay state mid-turn, and multiple
systems competing for touch input. The GDDs already specify signal boundaries (GSM Rule 9:
"does not call any command methods on DCS"; VMV EC-18; P&E EC-3) but they are scattered across
documents and need one enforceable contract.

### Current State

- No signals, no Autoloads, no code exist yet — this decision is made before implementation.
- The GDDs define ~25 signals across NPCRegistry, DCS, GSM, RFS, SaveLoad, MTF, P&E, HUD.
- MTF GDD Rules 1/9 establish MTF as the input boundary; Conversion UI Rule 2 makes it the blocking-layer owner — but nothing prevents a second owner from being introduced later.

### Constraints

- Signal-only boundaries must not block the enumerated command edges (VMV→`request_end_turn()`, VMV→`begin_conversation()`, UI→DCS commands, GSM→`process_turn()` stubs).
- Input must funnel through MTF (Rules 1, 9); UI must never read `Input` directly.
- Godot signals are synchronous and fire in connect order — subscription order matters (ADR-0001's deferred connect).
- `village_cleared` must reach DCS for recency reset (DCS GDD correction, Appendix A).

### Requirements

- Every cross-system interaction is either a named signal or an enumerated command edge — nothing else.
- Exactly one input boundary (MTF) and exactly one blocking-layer owner (Conversion UI).
- Signal inventory is auditable in one place (architecture.md §5) and enforced by `/architecture-review`.

## Decision

1. **Signal-only boundaries** (no method calls across, except enumerated commands):
   - **GSM ↔ DCS**: GSM subscribes `session_begun` / `session_complete`; never calls DCS methods (GSM Rule 9).
   - **VMV → DCS/gameplay**: VMV calls exactly one command — `request_end_turn()` — plus scene handoff `begin_conversation(npc_id)`; everything else via signals.
   - **HUD → gameplay**: snapshot reads only, inside `village_won`/`village_lost` handlers; never subscribes `npc_state_changed` (P&E EC-3 discipline).
2. **Enumerated command edges** (the complete list): VMV→`request_end_turn()`; VMV→`begin_conversation()`; Conversion UI→DCS (`begin_session`, `select_approach`, `trigger_inspect`, `cancel_session`, `get_approach_alignment`); GSM→`RivalFaithSystem.process_turn()` (Step 5) and GSM→`FaithSpreadSystem.process_turn()` (Step 4, no-op stub at MVP); SaveLoad→GSM/NPCRegistry (`get_save_data`/`serialize` etc.).
3. **MTF sole input boundary**: all touch input consumed by `MobileTouchFramework._input()`; UI registers targets via `register(control, priority)`; signals `tapped`, `long_press_started`, `long_press_released`, `swiped`, `touch_cancelled`.
4. **Blocking-layer ownership**: only the Conversion UI may call `push_blocking_layer()` / `pop_blocking_layer()` while a conversation session is open; any second owner is a review failure (guardrail).
5. **Signal inventory** lives in `docs/architecture/architecture.md` §5 — the table is the contract; new signals are added there and to entities.yaml, never ad hoc.

### Architecture

```
NPCRegistry ──npc_state_changed──► GSM, VMV        (HUD: snapshot only)
DCS ──session_begun/session_complete──► GSM, Conversion UI, SaveLoad, VMV, HUD
GSM ──village_ready/turn_*/village_*/faith_power_changed──► VMV, HUD, RFS, SaveLoad
GSM ──village_cleared──► DCS (recency reset) · VMV · HUD · Conversion UI
RFS ──rival_acted──► VMV (marker) · HUD (stamp/gauge)
SaveLoad ──load_*/save_*──► VMV, HUD
MTF ──tapped/long_press_*/swiped/touch_cancelled──► Conversion UI, VMV, HUD
Conversion UI ──conversation_closed──► VMV (single resume signal)

Command edges (only): VMV→request_end_turn · VMV→begin_conversation
                     UI→DCS commands · GSM→RFS.process_turn · GSM→FaithSpread.process_turn(stub)
```

### Key Interfaces

```gdscript

signal village_ready(village_id: String)

signal village_cleared()

# DCS — session orchestrator

signal outcome_resolved(outcome: GameEnums.ConversionOutcome, summary_line: String, revealed_trait_id: String)

# MTF — sole input boundary
signal tapped(target: Control, position: Vector2)

func unregister(control: Control) -> void

func pop_blocking_layer(id: String) -> void
```

### Implementation Guidelines

- Subscribers connect in `_ready()` (or `call_deferred` where the emitter may boot later — ADR-0001).
- Command edges are the exception, not the rule: if a new call crosses an orchestration boundary, it must be added to this ADR + architecture.md §5 first.
- MTF must not call `set_input_as_handled()` unless a registered target consumed the event (architecture risk R3).
- Blocking-layer ownership is enforced by code review and `/architecture-review` (guardrail, control-manifest).

## Alternatives Considered

### Alternative 1: Direct method calls across orchestration layers

- **Description**: Systems call each other's public methods freely; signals only for UI refresh.
- **Pros**: Simple, fast to write, easy to trace with an IDE.
- **Cons**: Violates GSM Rule 9 and the GDDs' explicit signal mandates; couples turn lifecycle to UI timing; harder to unit-test in isolation.
- **Estimated Effort**: Lower per call, higher to reason about the whole.
- **Rejection Reason**: The GDDs explicitly mandate signal-only boundaries; direct calls would make GSM/DCS/HUD ordering a hidden dependency.

### Alternative 2: Central event bus singleton

- **Description**: One global `EventBus` Autoload that all systems publish to and subscribe from.
- **Pros**: One import for everything; decoupled emitters/subscribers.
- **Cons**: Adds an 11th Autoload the GDDs don't mandate; loses per-emitter type safety; makes subscriber ordering implicit and harder to audit; Godot node signals already provide this without indirection.
- **Estimated Effort**: Similar.
- **Rejection Reason**: Native Godot signals on the owning Autoloads satisfy the requirement with less machinery and better discoverability; a bus would duplicate the signal inventory behind an extra layer.

## Consequences

### Positive

- Orchestration layers (GSM↔DCS, VMV→gameplay, HUD→gameplay) are decoupled and testable in isolation.
- MTF's single input boundary prevents input-order bugs (architecture risk R3) and keeps dp conversion in one place.
- One blocking-layer owner prevents modal-stack conflicts during conversations.
- The signal inventory is auditable in architecture.md §5.

### Negative

- Signal-only code is harder to trace with an IDE than direct calls (mitigated by the inventory table).
- Synchronous signal order must be respected (connect order / deferred connects) — a discipline cost.

### Neutral

- New consumers subscribe to existing signals without touching emitters — additive change.
- `village_cleared` now carries the recency-reset responsibility (DCS GDD wording fixed, Appendix A).
