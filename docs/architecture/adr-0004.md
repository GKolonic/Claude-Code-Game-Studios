# ADR-0004: Scene Ownership & CanvasLayer Stack

## Status

Accepted — 2026-08-09 (M0 foundation; approved by Creative Director)

## Summary

Presentation lives in four scenes — `main.tscn` (boot/router), `village_map.tscn` (per village),
`hud_progress.tscn` (per playthrough, survives clears), `conversation_screen.tscn` (per session) —
rendered on a three-layer CanvasLayer stack (0 = map, 1 = HUD, 2 = conversation). `PortraitController`
is a scene node owned by the conversation scene, not an Autoload.

## Context

### Problem Statement

The presentation GDDs (P&E, Conversion UI, VMV, HUD) explicitly forbid Autoload presentation:
"a scene, not an Autoload" appears four times. The ownership boundary between scenes and Autoloads
must be pinned, along with the render stack and the lifecycle that stitches the scenes together
(boot → village → conversations → resolution → title).

### Current State

- No scenes exist; `src/` is empty.
- GDD mandates: Conversion UI Rule 1 (scene, one per conversation), VMV Rule 1 (scene, one per village), HUD Rule 2 (scene, one per playthrough, kept across village transitions), P&E Rule 10 (PortraitController "**not an Autoload**", one per conversation).
- Save&Load OQ-02 implies a dedicated boot scene calling `load_game()`; HUD OQ-4 implies a title return at MVP.

### Constraints

- Scenes must never be registered as Autoloads (four explicit GDD rules).
- ConversationScreen covers the HUD during sessions (VMV AC-05 / Conversion UI Rule 17) → needs a CanvasLayer above HUD.
- HUD must survive `village_cleared` → it cannot be a child of the village scene.
- Scene names are GDD-pinned snake_case (`conversation_screen.tscn`, `village_map.tscn`, `hud_progress.tscn`) — minor deviation from PascalCase convention, flagged not blocked.
- Godot `CanvasLayer` ordering and scene instantiation are stable pre-cutoff APIs.

### Requirements

- One scene per presentation system, instantiated with the correct lifetime (per-conversation / per-village / per-playthrough).
- A deterministic render order: map at the bottom, HUD above, conversation on top.
- A single teardown/resume contract between VMV and ConversationScreen (`conversation_closed` on every path).
- Router returns to title at MVP (HUD OQ-4).

## Decision

1. **Four scenes, no presentation Autoloads**:

| Scene | Lifetime | Owner/Instantiator |
|-------|----------|--------------------|
| `main.tscn` | process | `project.godot` `main_scene` — boot/router |
| `village_map.tscn` | per village | `Main` (on `village_ready`/`load_completed`) |
| `hud_progress.tscn` | per playthrough | `Main` (once, survives clears) |
| `conversation_screen.tscn` | per session | `VillageMap` (on tap) |

2. **CanvasLayer stack** (rendering only — MTF ignores layer values for input priority):
   - Layer **0** = `VillageMap` (map background, markers, ink-bleed, End Turn button)
   - Layer **1** = `HudProgress` (top strip, detail panel, chronicle card)
   - Layer **2** = `ConversationScreen` (transient — covers HUD during sessions, VMV AC-05)
3. **`PortraitController`** is a scene node inside `conversation_screen.tscn` (`portrait_controller.tscn`), instantiated by the Conversion UI, one per conversation (P&E Rule 10).
4. **Lifecycle**:
   - `Main` (boot) calls `SaveLoadSystem.load_game()` once.
   - On `load_completed`/`village_ready`: instantiate VMV (per village) + HUD (once).
   - VMV instantiates ConversationScreen per tap; resumes on `conversation_closed` (emitted on **every** teardown path).
   - On `village_cleared`: VMV frees; HUD stays.
   - On `resolution_complete`: router returns to title (MVP); macro-layer seam post-MVP.

### Architecture

```
res://src/scenes/main.tscn  (Main — boot/router; main_scene)
│
├─ [CanvasLayer 0] VillageMap        — per village; freed on village_cleared
│   └─ instantiates ConversationScreen on tap
├─ [CanvasLayer 1] HudProgress       — per playthrough; survives clears
└─ [CanvasLayer 2, transient] ConversationScreen — per session
    └─ PortraitController (scene node, NOT Autoload)
```

### Key Interfaces

```gdscript
# Main (boot/router)
func _ready() -> void:
    SaveLoadSystem.load_game()          # once, after Autoloads ready (ADR-0001)
    # on village_ready/load_completed → instantiate VillageMap + HudProgress
    # on resolution_complete → return to title (MVP)

# VillageMap → ConversationScreen handoff
func _on_tapped(target, position) -> void:
    var conv := conversation_screen.instantiate()
    add_child(conv)                     # added to CanvasLayer 2
    conv.begin_conversation(npc_id)

# Teardown contract: ConversationScreen emits conversation_closed on EVERY path
# (session complete, back/cancel, defensive village-clear) — VMV resumes on it.
```

### Implementation Guidelines

- Scenes are presentation-only: they read Autoloads and subscribe to signals (ADR-0003); gameplay logic stays in Autoloads/plain classes.
- HUD is a sibling (not child) of VillageMap under `Main`, so it survives village transitions.
- CanvasLayer 2 is transient: ConversationScreen must not outlive its session; defensive teardown on `village_cleared` (Conversion UI Rule 17).
- MTF input priority is independent of CanvasLayer values (ADR-0003) — do not rely on layer order for input.

## Alternatives Considered

### Alternative 1: Presentation Autoloads (scene singletons)

- **Description**: Register conversation screen / map / HUD as Autoload scenes.
- **Pros**: Global access from anywhere.
- **Cons**: Directly violates four explicit GDD rules ("NOT an Autoload"); one-per-conversation becomes manual node juggling; HUD "survives clears" would require manual reparenting.
- **Estimated Effort**: Lower initially, higher for lifecycle correctness.
- **Rejection Reason**: The GDDs are explicit; Autoload presentation breaks per-instance lifetimes.

### Alternative 2: Single mega-scene with show/hide panels

- **Description**: One scene containing map + HUD + conversation layers toggled by visibility.
- **Pros**: One instantiation; trivial cross-panel access.
- **Cons**: Violates per-village/per-conversation instantiation; memory grows with the village; teardown/reset is manual; conflicts with the GDDs' scene-per-system framing.
- **Estimated Effort**: Similar.
- **Rejection Reason**: Per-instance scenes match the GDD mandates and give cleaner memory/lifecycle semantics.

## Consequences

### Positive

- Four scene lifetimes map 1:1 to the GDD mandates; no presentation Autoloads.
- CanvasLayer stack gives deterministic render order and the required conversation-over-HUD cover.
- HUD survives village transitions by construction (sibling under Main).
- `conversation_closed` single-resume contract makes every teardown path safe.

### Negative

- Scene handoff (VMV ↔ ConversationScreen) adds a small orchestration layer — the resume contract must be honored on every path (enforced by Conversion UI AC).
- `main.tscn` boot must coordinate `load_game()` timing with scene instantiation (ADR-0001 order + M4 tests).

### Neutral

- GDD-pinned snake_case scene names deviate from PascalCase naming convention (flagged in architecture.md §7, not blocking).
- CanvasLayer values are rendering-only; MTF input priority is handled separately (R3).
